# 界面与体验

## 总体体验目标

`teamaligned` 的界面应该像一个现代聊天软件，但背后具备完整的本地 Agent 执行能力。

用户应该感受到：

- 熟悉
- 轻量
- 有组织
- 能执行真实工作

而不是：

- 一个复杂后台
- 一个参数很多的 AI 控制面板
- 一个偏开发者内部工具的界面

当前这版 UI 已经明确采用“克制信息密度”的方向：

- 小字说明尽量减少
- 固定快捷命令入口不常驻
- 页面优先展示主任务和主操作
- 设置、扩展、管理页尽量接近 Figma 的单页应用感

## 基于 Figma 原型确认的全局骨架

当前原型已经明确了第一版桌面应用壳层：

- 左侧全局导航栏
- 顶部标题栏
- 页面主体区域
- 通知面板
- 个人资料弹窗

### 左侧全局导航

当前主导航包含 4 个主入口：

- 对话
- 管理
- 扩展
- 设置

仪表盘当前已从主导航移除，后续如果要恢复，需要先明确它是否真的承担独立用户任务。

并且支持：

- 收起 / 展开
- 主题切换

这说明全局导航需要兼顾“轻量”和“常用操作可直达”。

### 顶部标题栏

原型中顶部栏承担：

- 当前页面标题
- 通知按钮
- 用户头像入口

因此顶部栏建议保持固定，作为应用级状态区。

## 对话页规范

对话页是默认首页，也是产品主舞台。

### 当前已落地结构

对话页采用主聊天区 + 轻量信息侧栏结构：

- 左侧：会话列表
- 中间：聊天线程
- 最右侧：默认收起的会话信息侧栏

### 会话列表

当前会话列表已经简化为：

- 搜索框
- Agent 会话
- 群组会话
- 未读数
- 最后一条消息预览
- 最后活动时间

当前实现中不再保留额外的“会话 / 最近对话”标题区，只保留搜索和列表本身，以减少视觉噪音。

### 聊天线程

当前线程区包含：

- 会话标题
- 会话头像
- 消息气泡
- 提及提示
- 输入框
- 表情按钮
- 附件按钮
- 群聊中的 `@` 按钮
- 发送 / 取消按钮

当前实现中已移除：

- `单聊 Agent / 群组协作` 这类次级小字
- 输入框上方常驻的 slash command 快捷 chips
- 输入框底部的 skill / MCP 状态小胶囊
- 输入框上方的运行详情卡片

保留原则是：让用户仍然知道“这里可以输入命令”，但不让命令提示本身占据页面主体。

### 命令式交互

单聊输入框需要支持命令前缀，至少包括：

- `/skills`
- `/mcp`
- `/<skill-id>`
- `/<prompt-alias>`

当前实现已经支持直接输入这些命令，但采用的是“上下文快捷方式”而不是“控制台命令”：

- 用户直接在输入框键入 slash command
- `/skills` 和 `/mcp` 作为内置管理命令，只在消息开头生效
- `/<skill-id>` 会临时使用某个 Skill 处理本轮消息，不永久切换会话
- `/<prompt-alias>` 会展开扩展页中定义的 Prompt 模板
- Skill 和 Prompt Alias 可以在文中出现，例如“帮我用 /prd 整理一下”
- 长任务控制通过输入区取消按钮完成

后续增强可以再补：

- 命令参数建议
- 更结构化的执行回显

### 复杂任务控制

单聊中的长任务必须支持可控运行状态。
当 Agent 正在执行需要较长时间的任务时，用户应能看到：

- 当前任务在运行中
- 是否可以取消
- 当前 run 的摘要与 token 消耗

当前实现采用的方向是：

- 输入区锁定，避免连续发送
- 发送按钮切换为取消
- 基本运行信息进入最右侧会话信息侧栏

消息层至少要支持：

- 用户消息
- Agent 消息
- 群组消息
- 提及通知型消息
- 运行状态消息
- 命令执行消息
- 取消状态消息

### 右侧上下文的产品处理

原型没有展示重型右侧上下文栏，这意味着第一版主界面更强调纯聊天体验。

当前实现已经确定：

- 第一版只保留默认收起的轻量会话信息侧栏
- 展开后展示 Token、workspace、Skill、MCP、运行状态和最近工具调用
- workspace 支持直接在 Finder 中打开
- 群组内部协作通过主线程中的内部消息与顶部开关切换
- 完整 run step 详情暂不常驻展示，后续可做成详情抽屉或弹窗

这样既贴合原型，又能保持聊天页干净。

## 管理页规范

原型中的“管理”页分成两个 tab：

- Agent 管理
- 群组管理

### Agent 管理

Agent 卡片展示：

- 头像
- 名称
- 角色
- 状态
- 描述
- 能力标签
- 工作目录
- 已完成任务数

创建 Agent 时，原型已经体现出以下表单项：

- 名称
- 角色
- 描述
- 能力标签
- 工作目录
- 头像上传

这意味着产品文档里应把“工作目录”和“能力标签”视为 Agent 的一等属性。

### 群组管理

群组卡片展示：

- 群组头像
- 名称
- 描述
- 成员数量
- 工作目录
- 成员头像叠放

创建群组时，原型体现出：

- 群组名称
- 描述
- 群组目标
- 成员选择
- 工作目录
- 头像上传

这说明 Team 管理不是抽象配置页，而是偏“组织搭建”体验。

当前实现中，管理页已经采用：

- 顶部 tab 切换
- 卡片式 Agent / 群组展示
- 创建弹窗
- 本地 workspace 打开入口
- 头像上传与即时预览

## 群组聊天规范

群组聊天不是“多个 Agent 各说各话”，而是一个有协作语义的空间。

### 群组体验原则

群组体验应尽量贴近“和一个真实团队聊天”：

- 主线程尽量像人类团队群聊
- manager 是默认沟通窗口
- specialist 不是默认抢麦发言
- 复杂协作过程默认折叠
- 用户只有在需要时才看到内部编排细节

### 群组上下文

每个群组会话都应维护一份共享上下文，至少包含：

- 群组当前目标
- 当前阶段
- 约束条件
- 相关文件或 workspace 摘要
- 已分派任务
- 关键决策记录

群组中的 Agent 必须知道这份上下文，这样它们才不会在没有背景的情况下重复提问或做冲突判断。

### Agent 之间通信

群组中 Agent 可以直接向其他 Agent 发起通信。
建议支持：

- 互相 `@`
- 向指定 Agent 转交任务
- 向 manager 汇报状态
- 在群内请求澄清或补充信息

### manager 与 specialist 的发言规则

建议 UI 和产品语义都遵守以下协议：

- manager 默认负责回应用户
- specialist 默认先在内部线程中给 manager 反馈
- manager 汇总后再在主线程回复

只有在少数场景下，specialist 才直接对用户发言，例如：

- 需要非常具体的专业确认
- manager 已授权 specialist 直接提问
- 用户已经明确在与某个 specialist 深入沟通

这类消息建议在 UI 中使用更明确的“`@你` + 角色名”样式，以告诉用户这是一次受控升级，而不是群组混乱。

### 群组发言规则

群组消息需要区分三种语义：

- 面向用户的发言
- Agent 间的协作沟通
- 系统级的状态提示

建议具体落到 UI 为：

- 面向用户的发言：默认展示在主线程
- Agent 间协作沟通：默认折叠，通过“显示内部协作”查看
- 系统级状态提示：轻量插入，不打断阅读节奏

### 群组中的状态反馈

群组不应该向用户暴露完整编排图，而应该提供轻量、接近真人协作的状态：

- 正在讨论
- 某成员处理中
- 等待你的确认
- 已汇总结论

这会比直接展示大量 tool log 更贴近聊天产品。

这样才能让用户清楚知道：

- 谁在对谁说话
- 为什么发言
- 这条消息是建议、执行结果还是中间过程

## 扩展页规范

当前扩展页只保留“扩展中心”，并与 Figma 原型保持一致：

- 顶部标题
- `Skills / MCP` tab
- 两列扩展卡片
- 安装 / 已安装状态按钮

当前不保留：

- 右侧说明栏
- 搜索栏
- 额外的命令建议区域

## 设置页规范

当前设置页已收敛成三块：

- 语言
- 外观
- 通知
- 模型配置

其中模型配置采用“单 provider 表单”：

- 一次只启用一个模型供应商
- `模型供应商 / Base URL / API Key / 模型` 在同一层级
- `supportsToolCalling` 和 `supportsStreaming` 采用开关样式
- 通过“保存并启用”立即切换

个人资料不再常驻在设置页中，而是通过右上角头像弹窗单独编辑。

### 群组运行状态

当群组任务复杂时，界面应能展示：

- 哪个 Agent 正在工作
- 哪个 Agent 正在等待其他 Agent
- 哪个任务已完成
- 哪个任务卡住了
- 当前群组上下文是否已更新

## 扩展页规范

原型中的扩展中心分为两个 tab：

- Skills
- MCP

每个扩展项具备：

- 图标
- 名称
- 描述
- 安装状态
- 安装按钮

因此在产品设计上，扩展中心至少要支持：

- 浏览
- 安装
- 已安装状态识别
- Skills 和 MCP 的分类展示

后续可以扩展：

- 启用 / 禁用
- 版本管理
- 权限提示
- 来源说明

## 设置页规范

原型中的设置页已经给出四个模块：

- 语言
- 外观
- 通知
- 模型配置

### 语言

支持：

- 简体中文
- English

这意味着产品第一版就要从结构上支持国际化。

### 外观

支持：

- 浅色模式
- 深色模式

### 通知

支持独立开关：

- Agent 完成通知
- 提及通知
- 群组消息通知

### 模型配置

原型中已经给出：

- 供应商
- Base URL
- API Key
- 模型

虽然原型默认展示的是 DashScope，但结合本项目目标，设置页正式文档需要明确：

- 第一版只支持 OpenAI 与 Qwen
- Qwen 默认通过 DashScope OpenAI-compatible 方案接入
- 命令式交互与复杂任务控制不放在设置页，而放在会话页和运行卡片里完成

## 仪表盘规范

原型中的仪表盘包含：

- 活跃 Agent
- 群组数量
- 今日任务
- Token 消耗
- 最近动态
- Agent 状态
- Token 趋势图
- Agent Token 分布图

这说明仪表盘应承担“总览”和“运行指标”职责。

但在产品优先级上，需要强调：

- 仪表盘是辅助页
- 默认首页仍应保持为对话页

## 通知与个人资料

### 通知

原型中的通知下拉具备：

- 未读状态
- 时间
- 类型感知
- 全部已读
- 查看全部

通知不只是视觉提示，未来应能跳转回对应的：

- 会话
- run
- artifact

### 个人资料

个人资料弹窗包含：

- 姓名
- 角色
- 团队
- 邮箱
- 简介
- 头像

并明确提示：

Agent 会根据用户信息了解用户身份，从而更好地协作。

这说明用户 profile 不是可有可无的装饰项，而是 Agent 协作上下文的一部分。

## 视觉方向

### 配色

原型采用：

- 紫色主色
- 浅色模式下偏灰白底色
- 深色模式下偏蓝紫黑背景

可以整理为这样的视觉基调：

- 主色：智能、协作、现代感
- 辅色：状态提示与分类
- 底色：安静、不喧宾夺主

### 圆角与卡片

原型整体使用较柔和的卡片与圆角体系，适合桌面聊天产品。

### 语言风格

界面文案整体偏简洁、偏产品化，说明正式实现时应避免技术术语直接暴露给普通用户。

## 交互补充建议

原型没有覆盖但建议在正式实现中加入：

- 输入框自动扩展高度
- 流式输出中的“正在生成”状态
- 工具调用的折叠展示
- run 完成后可快速打开产物
- 群组内 `@agent` 自动补全
- 会话内搜索
