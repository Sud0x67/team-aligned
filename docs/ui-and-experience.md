# 界面与体验

## 总体体验目标

`teamaligned` 的界面应该像一个现代聊天软件，但背后具备完整的本地 Agent 执行能力。

用户应该感受到：

- 熟悉
- 轻量
- 有组织
- 能执行真实工作

而不是：

- 一个复杂后台
- 一个参数很多的 AI 控制面板
- 一个偏开发者内部工具的界面

## 基于 Figma 原型确认的全局骨架

当前原型已经明确了第一版桌面应用壳层：

- 左侧全局导航栏
- 顶部标题栏
- 页面主体区域
- 通知面板
- 个人资料弹窗

### 左侧全局导航

包含 5 个主入口：

- 对话
- 管理
- 扩展
- 仪表盘
- 设置

并且支持：

- 收起 / 展开
- 主题切换

这说明全局导航需要兼顾“轻量”和“常用操作可直达”。

### 顶部标题栏

原型中顶部栏承担：

- 当前页面标题
- 通知按钮
- 用户头像入口

因此顶部栏建议保持固定，作为应用级状态区。

## 对话页规范

对话页是默认首页，也是产品主舞台。

### 当前原型结构

对话页采用双工作区结构：

- 左侧：会话列表
- 右侧：聊天线程

### 会话列表

会话列表包含：

- 搜索框
- Agent 会话
- 群组会话
- 未读数
- 最后一条消息预览
- 最后活动时间

这说明“对话列表”不是一个简单联系人列表，而是带即时状态的消息导航器。

### 聊天线程

线程区包含：

- 会话标题
- 类型标记
- 群组成员摘要
- 在线状态
- 消息气泡
- 提及提示
- 输入框
- 附件按钮
- `@` 按钮
- 表情按钮
- 发送按钮

### 命令式交互

单聊输入框需要支持命令前缀，至少包括：

- `/skills`
- `/command`
- `/mcp`

这些命令不能只是文案提示，而应具备明确交互行为：

- `/skills` 用来查看、选择、启用或切换技能
- `/command` 用来执行本地命令、触发任务模板或系统级指令
- `/mcp` 用来查看可用 MCP、选择工具或发起调用

命令触发后，界面应立即给出反馈，例如：

- 弹出建议列表
- 显示当前可用项
- 记录已选技能或工具
- 标记命令已执行

### 复杂任务控制

单聊中的长任务必须支持可控运行状态。
当 Agent 正在执行需要较长时间的任务时，用户应能看到：

- 当前任务在运行中
- 是否可以暂停
- 是否可以继续
- 是否可以取消

建议在消息线程中直接展示任务控制条或运行卡片，而不是把这些能力藏在设置页里。

消息层至少要支持：

- 用户消息
- Agent 消息
- 群组消息
- 提及通知型消息
- 运行状态消息
- 命令执行消息
- 暂停、继续、取消状态消息

### 右侧上下文的产品处理

原型没有展示常驻右侧上下文栏，这意味着第一版主界面更强调纯聊天体验。

为了兼容长期产品设想，建议：

- 第一版不放常驻右栏
- 上下文以弹层、抽屉或详情面板出现
- 群组成员、任务、workspace、artifacts 作为按需展开内容

对于单聊，上下文面板主要展示：

- 当前 Agent 使用的技能
- 当前命令上下文
- 运行状态
- 可用 MCP
- 暂停、继续、取消入口

对于群聊，上下文面板主要展示：

- 群组共享上下文
- 当前参与的 Agent
- 群组内的待处理任务
- 群组内已发出的提及和委派
- 当前群组的 workspace 与记忆摘要

这样既贴合原型，又不会丢失后续扩展方向。

## 管理页规范

原型中的“管理”页分成两个 tab：

- Agent 管理
- 群组管理

### Agent 管理

Agent 卡片展示：

- 头像
- 名称
- 角色
- 状态
- 描述
- 能力标签
- 工作目录
- 已完成任务数

创建 Agent 时，原型已经体现出以下表单项：

- 名称
- 角色
- 描述
- 能力标签
- 工作目录
- 头像上传

这意味着产品文档里应把“工作目录”和“能力标签”视为 Agent 的一等属性。

### 群组管理

群组卡片展示：

- 群组头像
- 名称
- 描述
- 成员数量
- 工作目录
- 成员头像叠放

创建群组时，原型体现出：

- 群组名称
- 描述
- 成员选择
- 工作目录
- 头像上传

这说明 Team 管理不是抽象配置页，而是偏“组织搭建”体验。

## 群组聊天规范

群组聊天不是“多个 Agent 各说各话”，而是一个有协作语义的空间。

### 群组上下文

每个群组会话都应维护一份共享上下文，至少包含：

- 群组当前目标
- 当前阶段
- 约束条件
- 相关文件或 workspace 摘要
- 已分派任务
- 关键决策记录

群组中的 Agent 必须知道这份上下文，这样它们才不会在没有背景的情况下重复提问或做冲突判断。

### Agent 之间通信

群组中 Agent 可以直接向其他 Agent 发起通信。
建议支持：

- 互相 `@`
- 向指定 Agent 转交任务
- 向 manager 汇报状态
- 在群内请求澄清或补充信息

### 群组发言规则

群组消息需要区分三种语义：

- 面向用户的发言
- Agent 间的协作沟通
- 系统级的状态提示

这样才能让用户清楚知道：

- 谁在对谁说话
- 为什么发言
- 这条消息是建议、执行结果还是中间过程

### 群组运行状态

当群组任务复杂时，界面应能展示：

- 哪个 Agent 正在工作
- 哪个 Agent 正在等待其他 Agent
- 哪个任务已完成
- 哪个任务卡住了
- 当前群组上下文是否已更新

## 扩展页规范

原型中的扩展中心分为两个 tab：

- Skills
- MCP

每个扩展项具备：

- 图标
- 名称
- 描述
- 安装状态
- 安装按钮

因此在产品设计上，扩展中心至少要支持：

- 浏览
- 安装
- 已安装状态识别
- Skills 和 MCP 的分类展示

后续可以扩展：

- 启用 / 禁用
- 版本管理
- 权限提示
- 来源说明

## 设置页规范

原型中的设置页已经给出四个模块：

- 语言
- 外观
- 通知
- 模型配置

### 语言

支持：

- 简体中文
- English

这意味着产品第一版就要从结构上支持国际化。

### 外观

支持：

- 浅色模式
- 深色模式

### 通知

支持独立开关：

- Agent 完成通知
- 提及通知
- 群组消息通知

### 模型配置

原型中已经给出：

- 供应商
- Base URL
- API Key
- 模型

虽然原型默认展示的是 DashScope，但结合本项目目标，设置页正式文档需要明确：

- 第一版只支持 OpenAI 与 Qwen
- Qwen 默认通过 DashScope OpenAI-compatible 方案接入
- 命令式交互与复杂任务控制不放在设置页，而放在会话页和运行卡片里完成

## 仪表盘规范

原型中的仪表盘包含：

- 活跃 Agent
- 群组数量
- 今日任务
- Token 消耗
- 最近动态
- Agent 状态
- Token 趋势图
- Agent Token 分布图

这说明仪表盘应承担“总览”和“运行指标”职责。

但在产品优先级上，需要强调：

- 仪表盘是辅助页
- 默认首页仍应保持为对话页

## 通知与个人资料

### 通知

原型中的通知下拉具备：

- 未读状态
- 时间
- 类型感知
- 全部已读
- 查看全部

通知不只是视觉提示，未来应能跳转回对应的：

- 会话
- run
- artifact

### 个人资料

个人资料弹窗包含：

- 姓名
- 角色
- 团队
- 邮箱
- 简介
- 头像

并明确提示：

Agent 会根据用户信息了解用户身份，从而更好地协作。

这说明用户 profile 不是可有可无的装饰项，而是 Agent 协作上下文的一部分。

## 视觉方向

### 配色

原型采用：

- 紫色主色
- 浅色模式下偏灰白底色
- 深色模式下偏蓝紫黑背景

可以整理为这样的视觉基调：

- 主色：智能、协作、现代感
- 辅色：状态提示与分类
- 底色：安静、不喧宾夺主

### 圆角与卡片

原型整体使用较柔和的卡片与圆角体系，适合桌面聊天产品。

### 语言风格

界面文案整体偏简洁、偏产品化，说明正式实现时应避免技术术语直接暴露给普通用户。

## 交互补充建议

原型没有覆盖但建议在正式实现中加入：

- 输入框自动扩展高度
- 流式输出中的“正在生成”状态
- 工具调用的折叠展示
- run 完成后可快速打开产物
- 群组内 `@agent` 自动补全
- 会话内搜索
