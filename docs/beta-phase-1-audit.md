# Beta 第一阶段审查

## 文档目标

这份文档对应 beta 计划的第 1 阶段：**审查关键用户主链路，并识别阻断点、信任问题和体验问题。**

本次审查不讨论新增 feature，只讨论当前版本中，用户是否能顺畅完成已有能力。

问题统一分为三类：

- `blocking`：阻断用户完成主链路
- `trust`：用户能做，但会怀疑产品是否可靠
- `polish`：不阻断，但明显影响体验

## 总体结论

当前版本已经具备：

- 可运行的桌面壳
- 真实的单聊模型链路
- 真实的群聊 manager / specialist 链路
- Skills / MCP / 本地工具的主能力

但从 beta 角度看，当前问题已经不在“功能有没有”，而在“用户链路是否完整”。

本次审查后，当前结论是：

- 单聊主链路：**基本可用**
- Provider 配置链路：**基本可用，但反馈还不够细**
- 群聊链路：**可用，但存在明确阻断点**
- Skill 链路：**可用，但引导与状态反馈不足**
- MCP 链路：**可用，但配置链路较长，成功反馈不够集中**
- 附件链路：**可用，但失败反馈不足**
- 首次启动链路：**能进入应用，但缺少 beta 级引导**

## 1. 首次启动链路

目标链路：

1. 启动应用
2. 初始化本地目录与数据
3. 看到稳定的启动态
4. 进入可操作主界面

当前状态：

- 启动页和启动失败页已经存在
- `~/.teamaligned` 会自动初始化
- 旧目录会自动迁移
- 应用能稳定进入主界面

发现的问题：

- `trust`：首次进入应用时，没有显式告诉用户“下一步先去配置 provider”
- `polish`：默认种子数据会让用户直接看到会话、Agent、群组，但产品没有说明这些是示例初始数据还是用户数据

结论：

- 首次启动没有硬阻断
- 但缺少 beta 级别的引导与心智说明

## 2. Provider 配置链路

目标链路：

1. 进入设置页
2. 选择 provider
3. 填 Base URL / API Key / 模型
4. 测试连接
5. 保存并启用
6. 回到聊天开始使用

当前状态：

- 设置页已支持 provider 选择、参数填写、API Key 显隐
- 已支持参数校验
- 已支持测试连接
- 已支持保存并启用成功态

发现的问题：

- `trust`：错误反馈还是集中在一块消息面板中，缺少字段级错误定位
- `trust`：保存按钮依赖先测试连接，逻辑是对的，但用户不一定理解“为什么保存失败”
- `polish`：保存成功后，缺少更强的“你现在可以去聊天了”下一步提示

结论：

- Provider 主链路已经跑通
- 重点是错误提示与下一步引导还不够顺滑

## 3. 单聊链路

目标链路：

1. 选择 Agent
2. 发送消息
3. 获得流式回复
4. 调用工具 / Skill / MCP
5. 查看 run、artifact、attachment、tool call

当前状态：

- 单聊真实模型链路已可用
- 已支持流式输出
- 已支持 `/skills`、`/command`、`/mcp`
- 已支持附件上传和图片预览
- 已支持 run 详情可视化

发现的问题：

- `trust`：虽然支持 `/` 自动补全，但当前仍偏“知道命令的人更容易用”，新用户仍需要自己理解命令模型
- `polish`：Skill 是否真的生效，当前缺少更直观的反馈
- `polish`：MCP 是否真的被当前会话启用，也缺少明确的会话级状态反馈

结论：

- 单聊主链路是当前最成熟的一条
- 接下来主要是“降低理解成本”和“增强状态可见性”

## 4. 群聊链路

目标链路：

1. 创建或进入群组
2. 发送任务
3. manager / specialist 协作
4. 查看协作结果与 run 详情

当前状态：

- 群聊真实编排已经接通
- manager / specialist 受控发言模型已经存在
- 内部协作可折叠显示

发现的问题：

- `blocking`：管理页里“发起对话”按钮对群组只是跳转到聊天页，但不会自动选中该群组会话，用户链路被打断
- `trust`：群聊复杂任务的失败恢复、边界状态和重新继续路径还没有完全收口
- `polish`：群聊从管理页进入会话的动作不够明显，整体“进入任务”动作仍偏弱

结论：

- 群聊能力本身存在
- 但“从管理页进入并真正开始协作”的链路还没有闭环

## 5. Skill 链路

目标链路：

1. 进入扩展页
2. 同步 catalog
3. 安装 Skill
4. 在管理页配置 Agent 白名单
5. 回到聊天激活并使用

当前状态：

- Skill registry、安装、白名单、prompt 注入、脚本执行已完成
- `/skills` 与 `/skills use` 已可用

发现的问题：

- `trust`：安装成功后，没有明确告诉用户“下一步去哪里把它用起来”
- `trust`：白名单配置和会话激活分散在不同页面，链路偏长
- `polish`：消息流 / run 详情里对“当前 Skill 已生效”的显示还不够明显

结论：

- Skill 是可用的
- 但用户仍然需要自己推理“安装 -> 白名单 -> 会话激活”这条链路

## 6. MCP 链路

目标链路：

1. 进入扩展页
2. 同步 catalog
3. 配置 MCP
4. 健康检查
5. 在管理页配置 Agent / Team 白名单
6. 回到聊天调用

当前状态：

- `stdio npx` 和 `HTTP + headers` 都已可用
- MCP 配置、健康检查、白名单和 tool discovery 已可用

发现的问题：

- `trust`：MCP 配置成功后，缺少更明确的“你现在可以在哪个 Agent / Team 中使用它”的反馈
- `trust`：MCP 链路跨“扩展 -> 管理 -> 聊天”三处页面，理解成本较高
- `polish`：常见 MCP 的模板和预填还不够完善

结论：

- MCP 主能力已经在
- 当前问题更偏链路理解成本和状态反馈不足

## 7. 附件链路

目标链路：

1. 在聊天中选择文件
2. 上传并预览
3. 随消息发送
4. 后续在消息和 run 中查看

当前状态：

- 附件可以保存到本地目录
- 消息流中可以显示附件
- 图片可以预览
- 运行时可以读取附件路径

发现的问题：

- `done`：上传过程已有明确的上传中、部分失败和失败提示 UI
- `polish`：目前只有点选上传，没有拖拽链路

结论：

- 附件链路基本可用
- 失败反馈已经补齐，后续只剩拖拽上传等 polish 项

## 当前优先级最高的问题

### Blocking

- 当前没有已知 blocking 项。管理页“发起对话”不能直接进入目标群组会话的问题已修复。

### Trust

1. 群聊复杂任务的失败恢复与边界行为仍需专项收口
2. Provider 错误反馈还不够字段级
3. Skill / MCP 的“下一步怎么用”反馈不足

### Polish

1. 首次启动缺少更明确的引导
2. Skill 生效状态展示不够清楚
3. MCP 配置成功后的使用指引不够清楚
4. 附件交互仍缺少拖拽体验

## 建议修复顺序

1. 先修群聊入口闭环问题
2. 再修 Skill / MCP / Provider / 附件的状态反馈问题
3. 再收口群聊失败恢复和统一错误态
4. 最后做首次启动与其他体验打磨
