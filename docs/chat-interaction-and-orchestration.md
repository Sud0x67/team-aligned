# 聊天交互与编排规范

## 文档目标

这份文档专门定义 `teamaligned` 中最核心的交互层：

- 单聊如何工作
- 群聊如何工作
- slash command 如何工作
- 复杂任务如何取消
- 多 Agent 如何通信
- 群聊中谁应该对用户发言

## 1. 单聊交互模型

单聊是用户与单个 Agent 的直接协作线程。

### 支持的输入类型

单聊至少支持四类输入：

- 自然语言
- slash command
- 附件
- 运行控制

### Slash Command

第一版正式支持以下命令：

- `/skills`
- `/mcp`
- `/<skill-id>`
- `/<prompt-alias>`

其中：

- `/skills` 和 `/mcp` 是内置管理命令，只在消息开头生效。
- `/<skill-id>` 是一次性 Skill 调用，不会永久切换会话 Skill。
- `/<prompt-alias>` 是用户在扩展页创建的自定义 Prompt 快捷方式。
- Skill 和 Prompt Alias 支持在文中使用，例如“帮我用 /prd 整理一下”。

### 当前输入框策略

当前 UI 已确定采用“极简输入区”：

- 不在输入框上方常驻展示 `/skills /mcp` 快捷 chips
- 用户通过直接输入 slash command 触发命令
- 单聊输入区保留表情、附件和发送 / 取消按钮
- 群聊输入区保留 `@`、表情、附件和发送 / 取消按钮

这么做的目的不是降低命令能力，而是减少会话页的视觉碎片。

### 当前已实现的输入增强

- 用户输入 `/` 时会弹出命令建议
- 输入框支持 `@` 成员选择
- `/skills` 与 `/mcp` 已接入真实本地状态
- `/<skill-id>` 与 `/<prompt-alias>` 已接入本轮运行时上下文
- 附件已支持上传与图片预览
- 单聊中的图片附件会作为多模态输入传给支持 vision 的模型
- slash 结果会直接以聊天消息形式展示

### 单聊中的复杂任务

当前实现中，当任务进入执行态时：

- 输入区会锁定，避免连续发送
- 发送按钮会切换为取消按钮
- 运行详情中也会保留取消入口

当前已实现：

- 查看 run 详情
- 查看产物、附件与工具调用

当前仍待补强：

- checkpoint 级恢复与失败回放

## 2. 群聊交互模型

群聊是用户和多个 Agent 的自然协作线程。

### 群聊的体验目标

群聊要尽量贴近“和一个真实团队聊天”的体验，而不是一个编排控制台。

因此第一原则是：

- 用户只面对一个主线程
- 默认不出现 manager 或主持人
- Agent 像真实群成员一样自然发言
- `@` 优先，未被点名时由系统按语义选择相关 Agent
- 复杂协作可以展示 Agent 之间公开 `@`
- 工具、MCP、命令执行结果优先整理成自然语言结论

### 群聊中的发言主体

群聊主线程可出现：

- 用户消息
- Agent 消息
- 系统消息
- 提及消息

### 面向用户的发言协议

默认规则：

- 用户消息直接进入群组线程
- 如果用户 `@Agent`，被点名 Agent 优先回应
- 如果用户没有 `@`，system orchestrator 根据语义选择 1 到 5 个 Agent
- 普通问题通常只选 1 到 2 个 Agent
- 多视角问题选择 2 到 4 个 Agent
- 复杂协作选择 3 到 5 个 Agent
- 没有新增观点的 Agent 应保持沉默

### 群聊中的 `@`

群聊必须支持：

- 用户 `@agent`
- Agent `@agent`
- Agent `@user`

建议行为：

- `@` 输入时弹出群组成员选择面板
- 被提及时生成消息内高亮与通知
- Agent 互相 `@` 只能触发下一小轮，不能无限循环

### 群聊硬边界

- 每个群组最多 5 个 Agent
- 每个用户消息开启一个 `team turn`
- 每个 `team turn` 最多 5 个小轮
- 每个 `team turn` 最多 50 条 Agent 消息
- 同一个 Agent 在同一个 `team turn` 中最多发言 10 次

### Agent 之间通信

Agent 间通信分为两种：

#### 公开协作

直接显示在群聊主线程中。

示例：

- `Designer @Frontend：新版原型已上传，请开始还原`
- `Backend @QA：接口联调已准备好，请开始验证`

#### 内部编排

system orchestrator 的发言选择、轮数控制和停止判断不作为群成员展示。

## 3. 群组上下文模型

每个 Agent 在群聊中都必须知道当前群组上下文。

群组上下文至少包含：

- 成员与角色
- 最近消息摘要
- 当前任务列表
- 当前活跃 run
- 共享 memory
- 共享 workspace 摘要
- 已产出的关键 artifacts

### 群组上下文的三层结构

建议把群组上下文拆成三层，而不是所有信息都扔进同一个 prompt：

- 共享上下文：当前阶段、关键约束、活跃任务、共享 artifact
- 会话摘要：当前线程最近几轮的压缩摘要
- 成员私有记忆：每个 agent 自己的长期记忆与偏好

这样可以避免：

- 所有 specialist 共享同一份混杂记忆
- 群组 prompt 越积越大
- 多 Agent 对同一信息的理解失控

### 上下文刷新时机

建议在以下时机刷新群组上下文：

- 用户发送新任务
- 新子任务被分配
- 某个 Agent 完成阶段性产出
- 运行恢复
- 群组共享记忆更新

## 4. 复杂任务控制模型

复杂任务应始终对应一个可追踪的 run。

### Run 状态

建议状态包括：

- 排队中
- 运行中
- 暂停中
- 已暂停
- 恢复中
- 已完成
- 已失败
- 已取消

### 暂停语义

第一版采用协作式暂停：

- 不再调度新的 step
- 尽量在当前 step 边界停下
- 为恢复记录 checkpoint

### 恢复语义

恢复时从最近 checkpoint 继续，而不是完全重新开始。

### 取消语义

取消后：

- 停止当前 run
- 保留已完成消息与产物
- 在会话中写入取消事件

## 5. 群聊后端交互协议

群聊后端不应被设计成传统聊天室后端，而应被设计成“本地任务编排后端”。

建议运行时流程：

1. 用户消息进入 team ingress
2. 系统构建群组共享上下文与 handoff 状态
3. 不可见 system orchestrator 选择发言模式和 Agent
4. 被选中的 Agent 依次在主线程自然发言
5. Agent `@` 触发接棒，handoff 状态持续写回
6. 执行意图触发 work item，并由 execution subagent 处理重任务
7. messages + updates 双轨流式回传
8. 事件、产物、状态、共享记忆统一落盘

### 主线程与内部线程

建议在产品和存储层都明确区分两套流：

- 主线程：用户可见的对话
- 内部运行状态：system orchestrator、tool / MCP 的运行过程

内部运行状态的存在是为了：

- 保留真实协作能力
- 不破坏聊天感
- 支持暂停、恢复、审计和回放

### 群聊中的运行状态表达

用户在主线程中应该看到的不是复杂图执行细节，而是轻量状态：

- 正在讨论中
- 某成员处理中
- 需要你的确认
- 已汇总结论

更详细的执行信息，例如：

- 子任务分派
- tool call
- MCP 调用
- specialist 内部对话

应放入可展开的 run 详情中。

运行中的 `system updates` 也需要持续进入“思考中”过程气泡，避免出现长时间静默导致“像卡住”的体验。

## 6. UI 建议

### 单聊

当前已落地：

- 当前运行控制条
- 极简输入区
- 命令按钮与 `@` 入口

后续建议补充：

- slash command 自动补全
- 当前 workspace 标识
- 命令执行的结构化结果卡片

### 群聊

当前已落地：

- 群组内部协作显隐开关
- 提及高亮
- 公开协作消息

后续建议补充：

- 当前参与 Agent 的轻量展示
- Agent `@你` 的特殊提示样式
- 当前协作摘要
- 当前活跃成员
- 群组上下文抽屉
- 内部协作详情入口

## 7. MVP 建议边界

为了控制复杂度，MVP 对这套交互的落地建议如下：

### MVP 必做

- 单聊支持 `/skills`、`/mcp`、`/<skill-id>`、`/<prompt-alias>`
- 单聊支持取消当前 run
- 群聊支持用户 `@agent`
- 群聊支持 Agent 公开互相 `@`
- 群聊支持共享上下文摘要
- 群聊默认由不可见 orchestrator 选择 1 到 5 个 Agent 自然发言
- 群聊限制最多 5 个成员、5 个小轮、50 条 Agent 消息
- 群聊执行模式支持 execution subagent、依赖等待提示、工具过程自然输出

### 后续版本再做

- 内部协作线程完整可视化
- 更细粒度的抢占式暂停
- 并行多 run 调度界面
- 群组上下文的自动压缩与长期记忆融合
