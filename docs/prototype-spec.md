# 原型对齐说明

## 参考原型

当前文档已根据以下 Figma 原型进行对齐和补充：

- `AI Agent Software Design`
- 链接：`https://www.figma.com/make/eYjmDPuPuYLV6n0ZvNqraa/AI-Agent-Software-Design?t=bHi5BacocNTlVB95-1`

该原型不是静态页面截图，而是一套包含页面结构和交互逻辑的 Figma Make 原型代码。

## 从原型中确认下来的事实

### 1. 产品主导航已经明确

导航结构不是模糊的，而是已经落定为：

- 对话
- 管理
- 扩展
- 仪表盘
- 设置

### 2. 主首页是聊天

路由入口默认进入对话页，而不是仪表盘，这与“聊天优先”的产品方向一致。

### 3. 管理页已经拆成 Agent 和群组两类

说明产品不是只面向“和 AI 对话”，也面向“组织和管理 AI 团队”。

### 4. 扩展页已经把 Skills 与 MCP 并列

这与我们之前的产品路线完全一致，说明扩展机制应该在 MVP 中成为一等能力。

### 5. 设置页已经把语言、主题、通知和模型配置纳入产品

这意味着“本地桌面应用”的用户体验已经不再是简单演示稿，而是具备完整应用雏形。

### 6. 原型中已经出现通知中心和用户资料

这会影响后续存储结构、事件模型与 Agent 上下文设计。

### 7. 原型是“聊天优先 + 管理辅助 + 扩展支撑”的结构

这意味着后续实现不能把产品重心拉回仪表盘或设置页，而应继续围绕对话组织所有主要交互。

## 当前实现已做出的取舍

在保持 Figma 原型信息架构的前提下，当前代码实现已经做了几项明确收敛：

### 1. 对话页继续保持双栏，但去掉噪音型辅助文案

当前会话页采用：

- 左侧仅保留搜索栏与会话列表
- 中间保留标题、消息流、输入区
- 不放常驻右侧上下文面板

并且已经移除：

- 左侧“会话 / 最近对话”标题区
- 输入框上方常驻 slash command chips
- 聊天头部的 `单聊 Agent / 群组协作` 次级小字

这属于有意识的产品级简化，而不是实现缺失。

### 2. 管理页按照 Figma 的 tab 结构落地

当前实现中：

- 管理页采用 `Agent 管理 / 群组管理` 双 tab
- Agent 和群组都使用卡片网格
- 创建弹窗支持头像上传
- 列表卡片也优先展示头像

### 3. 扩展页只保留扩展中心

当前扩展页对齐 Figma 的核心结构：

- `Skills / MCP` tab
- 扩展卡片
- 安装 / 已安装状态

没有继续保留额外的右侧说明区或搜索区。

### 4. 设置页做了“单 provider”收敛

当前设置页采用：

- 语言
- 外观
- 通知
- 模型配置

其中模型配置一次只启用一个 provider，避免早期产品同时维护多套启用态。

### 5. 个人资料改由右上角头像入口承担

设置页中不再保留“个人资料设置”区块，个人资料与用户头像统一通过顶部头像弹窗编辑。

## 需要基于原型补充的实现细节

原型给出了主要界面，但还有一些运行时细节需要文档补充：

### 对话与运行的关系

原型展示了聊天页，但没有展开 run、tool call、artifact 的具体视觉层级。

文档补充建议：

- 聊天线程仍是主容器
- run 作为结构化消息块插入线程
- artifact 可以作为消息附件或可展开卡片出现
- 长任务的运行卡片需要支持暂停、继续和取消
- 命令触发的任务应在消息流里留下清晰痕迹

### 单聊命令交互

原型中的输入框需要扩展成“可输入自然语言，也可输入命令”的交互区。

文档补充建议：

- `/skills` 用于查看和切换技能
- `/<prompt-alias>` 用于执行用户自定义 Prompt 模板
- `/mcp` 用于查看和调用 MCP
- 命令执行后应返回结构化反馈，而不是只有纯文本回复
- 是否常驻展示命令入口可以根据页面密度收敛，当前实现选择“支持命令，但不常驻展示命令 chips”

### 群组的内部编排

原型展示了群组对话，但没有展开 manager / specialist 的内部代理关系。

文档补充建议：

- 群组对外显示为统一会话
- 内部由 manager agent 协调 specialist subagents
- 用户可以通过 `@agent` 指定对象
- 群组中的 Agent 之间也可以互相 `@`
- 群组上下文必须对所有参与的 Agent 可见
- Agent 需要知道当前群组的目标、约束和任务状态

进一步的产品级补充建议：

- manager 是默认的主发言人
- specialist 默认先在内部线程中协作
- 只有在必要时，specialist 才直接 `@用户`
- specialist 直接 `@用户` 应被视为一次受控升级，而不是默认行为

### 群组上下文的展示方式

建议把群组上下文表达为一个轻量但明确的共享状态区：

- 当前目标
- 当前任务
- 关键文件
- 相关成员
- 已完成进展
- 待确认问题

这样可以让群聊既保留聊天感，也具备真正的团队协作语义。

### 群组后端的真实落地方向

虽然原型主要体现前端信息架构，但结合当前产品路线，群组真正的后端建议采用：

- local-first 本地运行时
- manager 中心化调度
- 主线程与内部线程分离
- 事件、产物、共享上下文统一落盘

这会让原型中的群组体验不仅“看起来像团队”，而且“运行起来也像团队”。

### 扩展的安装后权限模型

原型展示了“安装”状态，但未体现权限边界。

文档补充建议：

- Skills 主要影响提示和工作流
- MCP 需要记录来源、协议类型和可访问范围
- 本地能力和外部能力需要分别提示

### 工作目录的用户表达

原型中多个页面都出现了 `workDir`，说明工作目录是核心概念。

文档补充建议：

- 创建 Agent / Team 时必须可设置工作目录
- 后续聊天页可提供“打开工作目录”“查看最近文件”等入口
- 长任务的暂停、继续、取消应出现在运行中的任务卡片或更多操作菜单里
- 创建 Agent / Team 时同时支持头像设置，以增强组织感和识别度

## 对正式实现的建议

### 保留原型的优点

应优先保留：

- 聊天作为默认首页
- 简洁的双区聊天布局
- 轻量全局导航
- 管理 / 扩展 / 设置的独立页面
- 主题与语言切换

### 对原型做产品级增强

建议增强：

- 会话级上下文面板
- run / artifact 可视化
- Agent 状态与执行状态统一
- 安装扩展的权限与来源说明
- 更贴近本地执行的文案与反馈

## 原型与最终技术实现的关系

当前原型是基于前端路由页面组织的 UI 原型，而正式产品会以 Electron + React + 本地 Runtime 实现。

因此实现时需要注意：

- 保留原型的信息架构和交互语言
- 不直接照搬原型的技术组织方式
- 用 Electron IPC 和本地运行时去承载原型里的交互语义
