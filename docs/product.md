# 产品定位

## 一句话定义

`teamaligned` 是一个本地优先的 AI Team 聊天应用。

用户既可以像聊天软件一样与单个 Agent 私聊，也可以在一个群聊里和整支 Agent 团队协作；每个 Agent 都拥有自己的 workspace、memory、skills 与 MCP 能力，并且可以在本地执行真实任务。

## 产品目标

这个产品要解决的不是“再做一个 AI 面板”，而是：

让用户把 AI 当作真正的协作对象来沟通、分工、追进度和查看结果。

用户第一眼看到的应该是：

- 对话
- 群组
- 任务进展
- 通知
- 可交付结果

而不是一堆抽象配置和复杂后台。

## 核心价值

### 1. 聊天优先

消息线程是主入口。任务、运行记录、文件、产物和设置都服务于聊天，而不是反过来。

### 2. 本地优先

配置、会话、记忆、工作目录和执行结果尽可能都保存在本地，方便用户掌控和审计。

### 3. 团队协作感

用户不仅能和单个 Agent 对话，还能和一个 Agent 团队在统一线程中协作，形成“经理 + 专家”的工作方式。

### 4. 可扩展

Skills 和 MCP 是内建能力，不是额外补丁。

### 5. 可审计

重要动作需要能被追踪到消息、运行记录、产物、文件修改和本地日志。

### 6. 可编排

单聊和群聊都不是简单问答，而是可编排的任务流。
用户可以通过命令、技能、MCP 和群组协作把复杂任务拆开执行，并在执行过程中暂停、继续或取消。

## 基于原型确认的产品信息架构

Figma 原型已经给出了第一版清晰的信息架构，主导航包括：

- 对话
- 管理
- 扩展
- 仪表盘
- 设置

其中：

- “对话”是默认主入口
- “管理”负责 Agent 与群组的创建和维护
- “扩展”负责 Skills 与 MCP 安装管理
- “仪表盘”提供总览和统计，但不应压过聊天主入口
- “设置”负责语言、主题、通知与模型配置

## 核心对象

### 用户

用户是本地应用的唯一操作者。在 MVP 中先按单用户场景设计。

### Agent

每个 Agent 至少包含：

- 身份信息
- 角色与能力标签
- 头像
- 状态
- 工作目录
- memory
- skills
- MCP 可用范围
- provider 与 model 配置

### 群组 / Team

群组用于组织多个 Agent 协作，至少包含：

- 群组名称与描述
- 群组头像
- 成员列表
- 群组工作目录
- 共享上下文
- 群组会话

### 会话

会话是主交互实体，分为两类：

- 单 Agent 私聊
- Team 群聊

### 命令

命令是会话中的显式操作入口，用于控制 Agent 的技能、工具和执行状态。
第一版至少要支持：

- `/skills`
- `/command`
- `/mcp`

### 任务状态

复杂任务需要具备清晰的运行状态：

- 运行中
- 暂停中
- 已恢复
- 已取消
- 已完成

### Run

一次由消息触发的执行过程，可能包括：

- 子 Agent 调度
- 工具调用
- 文件读写
- 命令执行
- 产物生成

### Artifact

运行产生的可交付结果，例如：

- 文件
- 摘要
- 报告
- 计划
- 补丁
- 可视化结果

## 关键用户场景

### 场景 1：直接和一个 Agent 私聊

用户进入“对话”页面，选择某个 Agent，发送请求，让它完成一个具体任务。
在这个场景里，用户可以直接通过命令控制交互，例如：

- 用 `/skills` 查看或切换技能
- 用 `/command` 触发预设动作或任务模板
- 用 `/mcp` 查看或调用可用 MCP
- 对长任务发出暂停、继续、取消指令

### 场景 2：在团队群聊里分工

用户进入某个群组会话，通过自然语言或 `@agent` 的方式在团队中分派工作、查看进度和接收产物。
群组中的 Agent 之间也可以互相通信，不是只对用户单向回答。
manager agent 需要理解群组上下文，并把共享上下文同步给参与协作的 specialist agents。

### 场景 3：管理 Agent 与群组

用户在“管理”页面中：

- 创建 Agent
- 为 Agent 设置头像
- 配置工作目录
- 维护能力标签
- 创建群组
- 为群组分配成员
- 为群组设置头像

### 场景 4：安装扩展

用户在“扩展”页面中安装：

- Skills
- MCP 服务

让 Agent 获得额外能力，例如网络搜索、GitHub 操作或知识库访问。

### 场景 5：调整本地偏好与模型

用户在“设置”页面中管理：

- 中英文切换
- 深浅色主题
- 通知开关
- 当前启用的模型供应商配置

个人资料则通过右上角头像入口单独编辑，包括：

- 姓名
- 角色
- 团队
- 邮箱
- 简介
- 用户头像

### 当前产品形态补充

结合当前代码实现，第一版产品形态已经收敛为：

- 对话页保持双栏，不使用常驻右侧上下文面板
- Slash command 继续支持，但不再以固定快捷 chips 常驻展示
- 管理页使用 `Agent 管理 / 群组管理` 双 tab
- 创建 Agent、创建群组、个人资料都支持头像上传
- 扩展页当前只保留“扩展中心”
- 设置页只允许一次启用一个 provider，通过单个表单保存并切换

## 产品原则

### 主入口必须是对话

无论未来能力扩展到什么程度，默认首页都应保持为对话，而不是统计总览。

### 管理视图要强，但不能抢主角

“管理”“扩展”“设置”都很重要，但它们是支持面，而不是产品核心体验。

### 仪表盘存在，但不应主导叙事

原型中有仪表盘，这对系统总览很有帮助；但在产品语义上，它应该是辅助页，不应把产品带回 dashboard-first。

### 移动复杂度，而不是制造复杂度

工具、运行细节、上下文与日志要分层露出，让主线程尽量轻。

### 命令优先于隐藏魔法

当用户想明确控制技能、工具或运行状态时，应提供可见、可理解的命令入口，而不是把能力埋在不可解释的自动化里。

## MVP 非目标

第一版不做：

- 多人在线协作
- 云同步
- 托管 workspace
- 分布式任务系统
- 过多模型供应商
- 重型后端服务
